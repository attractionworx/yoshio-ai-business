# Yoshio AI Business

コンテンツのテーマや読者を整理し、このMacに保存するローカルWebアプリです。
ブログ・アフィリエイト記事、note、SNS、YouTubeなどの制作準備に使えます。

Phase 2では、企画からCodexへの生成依頼文を作り、Codexの回答を取り込んで編集・確認できます。このアプリは外部APIへ接続せず、自動投稿もしません。アプリの利用にAPIキーは不要です。Codexの利用料金・上限は利用中の契約と認証方式に従います。

## 1. 起動方法

Node.js 22以上を使用します。今回の環境ではNode.js 24で確認しています。

Macの「ターミナル」を開いて、次のコマンドを1行ずつ実行してください。

```bash
cd /Users/yoshio/yoshio-ai-business
npm install --cache .npm-cache --ignore-scripts --no-audit --no-fund
npm start
```

`npm install`は初回に実行します。追加のnpmパッケージに依存せず、Node.jsの標準機能だけで動きます。2回目からはフォルダへ移動して`npm start`だけで起動できます。

起動メッセージが出たら、SafariやChromeのアドレス欄に以下を入力してください。

**http://127.0.0.1:3000**

起動中はターミナルを開いたままにします。

### 使い方

1. 「コンテンツのテーマ」を入力します（必須・200文字まで）。
2. ターゲット読者を入力します（任意・500文字まで）。
3. 媒体をブログ / note / X / Instagram / YouTubeから選択します。
4. 目的（1,000文字まで）とメモ（5,000文字まで）を必要に応じて入力します。
5. 「企画を作成」を押すと保存され、整理した内容が表示されます。
6. 「企画一覧・新規作成へ」から、保存した企画を開いたり、新しい企画を作成したりできます。

前後の空白は取り除いて保存します。未入力の任意項目は詳細画面で「未入力」と表示します。各企画は独立したファイルになり、同じテーマでも別の企画として保存されます。詳細画面を再読み込みしても追加保存されません。

### 起動できないとき

- `node`や`npm`が見つからない場合は、Node.jsが利用できるターミナルか確認してください。
- 「ポート3000が使用中」と表示された場合は、先に起動したアプリのターミナルで`Control + C`を押してから再実行してください。
- 保存や表示に失敗した場合は、ターミナルのエラーと`data/`フォルダを確認してください。データを手動編集してJSONの形式が壊れると、読み込めなくなる場合があります。削除せずバックアップを取ってから確認してください。

## 2. 終了方法

起動に使ったターミナルで **Control + C** を押します（Commandキーではありません）。
ブラウザを閉じるだけではアプリは終了しません。終了後も企画ファイルは残ります。再び`npm start`で起動すると、保存済みの企画を開けます。

### 秘密情報とローカル利用

- APIキーなどの秘密情報をコードへ直接書かないでください。将来APIを追加するときは、環境変数などからサーバー側で読み込みます。
- `.env`、`.env.*`（`.env.example`を除く）、`secrets/`、秘密鍵、企画データ、npmキャッシュは`.gitignore`で除外しています。`.env.example`を作る場合はダミー値だけにしてください。
- 現段階では`.env`の読み込み処理はありません。秘密情報の入力も不要です。
- `.gitignore`はコードなどへ直接書いた秘密情報や、すでにGitへ登録済みのファイルを保護するものではありません。公開前には変更内容を確認してください。
- アプリは`127.0.0.1`だけで待ち受けます。ログイン機能はなく、このMacでの個人利用を想定しています。保存ファイルは暗号化していません。

実際のブラウザでも確認するには、Google ChromeがインストールされたMacでアプリを起動し、別のターミナルから以下を実行します。


## 4. Phase 2：Codexで下書きを作る手順

### ① アプリで企画を保存する

`npm start`で起動し、http://127.0.0.1:3000 を開きます。テーマ・ターゲット読者・媒体・目的・メモを入力して「企画を作成」を押します。保存済みの企画を一覧から開いても使えます。

### ② 依頼文をコピーしてCodexへ渡す

企画詳細の「1. Codexへの依頼文」にある「依頼文をコピー」を押します。Codexで新しい会話を開き、貼り付けて送信します。企画IDや出力形式も含め、依頼文全体を渡してください。回答待ちの間、アプリは開いたままで構いません。

コピーが許可されない場合は依頼文が選択されるので、Macでは **Command+C** でコピーできます。JavaScriptを無効にしている場合も、依頼文欄をクリックしてCommand+A、Command+Cでコピーできます。

アプリ自体は外部AIと通信しません。ただしCodexに貼り付けた情報はCodexへ渡ります。APIキー・パスワード・公開できない個人情報は含めないでください。APIを使わない運用では、Codex側もAPIキー認証ではなく、利用中のChatGPT契約での利用を選んでください。利用枠を超える追加購入はこのアプリでは行いません。

### ③ Codexの回答を取り込む

Codexは、次の7項目を含むJSON（アプリが読める形式の文章）を返します。

1. 企画概要
2. タイトル候補5個
3. 想定読者の悩み・検索意図
4. 記事・コンテンツの構成
5. 本文の下書き
6. CTA案
7. SNS告知文

Codexの回答をコピーし、企画詳細の「2. 生成結果を取り込む」へ貼り付けて「新しい下書きとして取り込む」を押します。JSONを囲むコードブロックや前後の説明文も含められます。回答が複数含まれる場合は、どれを使うか推測せず拒否するため、1つの回答だけを貼り付けてください。

コピーした文章に画面の折り返しが混ざると、文の途中に実際の改行と字下げが入り、JSONとして読み取れなくなることがあります。この場合は、文字列内の実改行と直後の字下げだけを除いたプレビューを表示します。JSONの`\n`で指定されている段落は保持します。

プレビューの時点では保存されていません。単語の間の空白や段落が意図どおりか確認し、「内容を確認して新しい下書きとして取り込む」を押してください。取り込まずに企画へ戻ることもできます。取り込み後も「貼り付け時の回答全文を見る」から補正前の文章を確認できます。

引用符やカンマの欠落、不正なエスケープ、同じ項目名の重複などは推測で修正しません。補正後も構文や必須項目が不正なら保存せず、エラーを表示します。

手でJSONを書く必要はありません。読み取りエラーになった場合は、画面のエラー文とともにCodexへ「このエラーを直して、元の企画ID・プロンプトバージョンを保ったJSON全体を再出力してください」と依頼します。エラー時は貼り付けた内容を画面に保持します。別企画の結果、7項目の欠落、タイトルが5個でない回答は保存しません。

取り込み直後の状態は必ず「未確認」です。APIによる自動生成や自動投稿は実行されません。

### ④ 7項目を編集して保存する

下書き画面で各項目を直接編集できます。タイトル候補は1行に1個、合計5行で入力します。「編集内容を保存」を押すと「編集中」になります。保存前にページを閉じると未保存の編集は残りません。

「AIが生成した原文を見る」を開くと、取り込み時の原文を確認できます。編集しても原文は変わりません。生成時の依頼文も確認できます。

### ⑤ 内容を確認済みにする

編集内容を保存し、事実・数値・リンク・表現などを読み直してから「確認済みにする」を押します。「確認済み」は人間が内容の確認を終えた記録です。このアプリから投稿はされません。

確認済みの文章を再編集すると、画面に「編集中（未保存）」と表示されます。保存すると保存データも「編集中」に戻ります。変更後はまず保存し、その後もう一度「確認済みにする」を押してください。変更せず保存した場合は確認済みを維持します。

### ⑥ 再生成と過去の下書き

既存の記事を改善する場合は、以下の「Phase 2.1」の手順を使ってください。親ドラフト付きの新しい版として保存できます。

「企画・過去の下書きへ」から元の企画に戻り、依頼文をもう一度Codexに渡します。修正したい方向性は、元の依頼文に添えてCodexへ伝えてください。元の企画IDとプロンプトバージョンを保ったJSONで回答するよう指定します。

結果を取り込むたびに新しい下書きができます。以前の下書きや編集内容は上書きされません。「過去の下書き」からそれぞれの原文・最新の編集内容・状態を確認できます。同じ下書き内の保存操作ごとの全履歴を残す機能ではありません。

複数のタブで同じ下書きを開いていた場合、古い画面からの保存は拒否されます。入力した文章を手元にコピーしてから、最新の下書きを開き直して反映してください。

## 5. 保存される情報とバックアップ

各下書きには、企画ID、生成時の企画、生成原文、貼り付けた回答全体、編集後の7項目、状態、確認日時、生成日時、取り込み日時、最終保存日時、生成方法、プロンプトのバージョン、生成依頼文を保存します。

生成方法は`codex-manual`です。生成日時はCodexの回答に含まれる申告値で、アプリが独立に検証した時刻ではありません。Codexで日時を取得できなければ`null`を返すよう依頼し、画面では「不明」と表示します。取り込み日時はアプリが実際に保存した時刻です。

`data/`全体はGit対象外です。アプリを停止し、フォルダ全体をコピーしてバックアップしてください。GitHubへコードを送っても下書きはバックアップされません。

バックアップはリポジトリ外の保護された場所に保存し、ファイル一覧とSHA-256で完全性を確認してください。

復旧する場合はアプリを停止し、現在の`data/`も別途バックアップしてから、アーカイブを新しい空フォルダへ展開して内容を確認してください。稼働中のプロジェクトへ直接上書きしないでください。

### 取り込み不具合の再発防止テスト

架空の検証専用文章を`test/fixtures/codex-note-response.json`、コピー時の折り返しを再現した文章を`test/fixtures/codex-pasted-wrapped.txt`に収録しています。実際の記事本文や企画IDは使用しません。後者には文字列内の折り返しが102か所あり、その除去後に7項目すべてが元の回答と一致することを検証します。

以前のテストは`JSON.stringify`で作った正しいJSONが中心で、画面からコピーした際の折り返しを検証できていませんでした。現在は`npm test`と`node scripts/browser-phase2.mjs`で、長文、説明文・コードブロック、折り返しを再現した回答、補正確認前の未保存、不正入力の拒否を検証します。ブラウザ検証では専用のクリップボード内容を使用するため、実行前に残したいコピー内容は別途控えてください。


## 7. Phase 2.1：下書き改善とバージョン履歴

### 通常の使い方

1. 企画から下書きを開きます。本文を編集した場合は先に「編集内容を保存」を押します。
2. 「AIで下書きを改善」の「改善依頼文を作る」を押します。
3. 表示された依頼文を「Codex用依頼文をコピー」でコピーし、Codexへ渡します。現在の企画と保存済みの人間編集版7項目を使用します。
4. この改善依頼画面を開いたままにし、Codexが返したJSONを貼り付けて「改稿を取り込む」を押します。画面のURLを保存しておけばアプリ再起動後も再開できます。
5. 改稿は必ず別ID・新しい版番号の「未確認」ドラフトになります。確認済みの親ドラフトや以前の版は変更されません。
6. 「バージョン履歴」からv1・v2・v3などを開き、状態・取り込み日時・改善方針・最新表示を確認します。元の下書きは「親ドラフトを開く」からも開けます。

通常は「読みやすくする」「初心者向けにする」「具体例を増やす」がONで、「完成稿を作る」を使います。「詳細設定」を開くと、「短くする」「SEOを意識する」「CTAを改善する」、自由入力の「その他の改善指示」（5,000文字以内）を指定できます。

実体験・収益・経歴・成功実績など、元データにない事実の創作禁止ルールはサーバー側で常に依頼文へ追加し、解除する設定はありません。具体例は仮の例と明示させます。既存ファイルを変更せず、まず回答として返す指示も含めます。AIの回答の事実性は人間が確認してください。

### 分析してから仕上げる

詳細設定の「まず分析だけする」を選ぶと、問題点・改善案・確認事項を返す依頼になります。分析結果の取り込みフォームは表示せず、サーバー側でも取り込みを拒否します。検討後、元の下書きで「完成稿を作る」を選び直し、必要な分析結果を「その他の改善指示」に反映して新しい依頼を作ります。

### 保存形式と互換性

- 新しいドラフトは`schemaVersion: 2`で、`versionNumber`（企画内の通し番号）、`parentDraftId`（改善元。初回・通常再生成はnull）、`improvement`（改善依頼のスナップショット）を追加します。編集保存回数の`revision`とは別です。
- `improvement`には設定、親の保存リビジョン、元本文、企画、依頼文、作成日時、依頼IDを保存します。回答待ちに親が編集されても、依頼作成時の内容を追跡できます。
- 改善依頼は`data/improvements/<依頼ID>.json`にも保存します。下書きと同様にGit対象外で、`data/`全体のバックアップに含めてください。
- 古いPhase 2ドラフトは移行・書き換えを行いません。版番号がないデータは取り込み日時順（同時刻ならID順）に表示用の番号を割り当て、新規ドラフトはその後に採番します。同じ企画の同時取り込みは1つのアプリ内で直列化します。同じデータフォルダへ複数のアプリを同時起動する運用は想定していません。
- 過去版から改稿すれば、その版を親とする分岐になります。版番号は枝ごとではなく企画全体の通し番号です。ツリー表示はありません。
- 改稿回答は企画ID・改善用プロンプトバージョン・依頼ID・親ドラフトIDがすべて一致する必要があります。通常の生成回答は従来の取り込み欄、改稿回答は対応する改善依頼画面に貼り付けます。
- コードブロック・周囲の説明文・安全な折り返し補正は既存処理を共有します。補正時はプレビュー確認後だけ保存し、貼り付け原文を保持します。曖昧な回答や壊れた入力を推測で補完しません。
- 同じ回答を再度取り込むと別の新規版になります。各版の「編集内容を保存」は従来どおりその版の人間編集欄を更新します。編集保存ごとの履歴は作りません。

状態は「未確認・編集中・確認済み」のままです。Phase 2.1では外部API連携、自動投稿、公開状態の管理は追加していません。

### 検証と実装前のバックアップ

```bash
npm test
node scripts/browser-phase2.mjs
```

### 料金概算と安全停止

- 月予算1,000円、800円から警告、使用済み＋保持予約＋今回の予約が900円を超える場合は生成前に停止します。
- 1回の予約上限は20円。標準設定の最大予約は10円です。
- Fakeモードではテスト用単価を使います。OpenAIモードではサーバーの概算単価と為替換算を使うため、実請求額とは一致しません。請求額はOpenAIの利用明細で確認してください。
- 標準Fakeのusageは入力1,000・出力2,000トークン、模擬概算3円です。成功時は10円予約を3円の模擬実績へ精算します。
- 月次集計はUTC月です。過去月の未解決予約も停止判定に含めます。
- Fakeモードの実API実行回数0・実料金0円と、模擬実行回数・保存件数を区別して表示します。OpenAIモードの金額は概算と表示します。
- 不正JSONなどでもusageを取得できた場合は模擬利用へ計上します。使用量不明・タイムアウトは0円とみなさず、予約を保持します。
- 同時生成は1件、自動再試行は0回。結果不明または中断した実行がある場合、新たな生成は停止します。
- 模擬料金表と実料金の集計を将来混ぜないよう、記録には`simulation: true`と料金設定の版を保持します。

### 保存・重複防止・復旧

`lib/ai/`で設定、Fake/OpenAI Provider、プロンプト、検証、生成サービス、実行記録、予算を分離しています。新規ドラフトはproviderに応じて`ai-direct-fake`または`ai-direct-openai`で記録します。状態は必ず未確認、reviewedAtはnull、parentDraftIdはnull、公開準備は未チェックです。原文JSONを保持し、originalとeditedを分離します。旧ドラフトは読み込みだけでは書き換えません。

実行記録は指定データフォルダの`generations/ledger.json`へ保存し、初期化マーカーとロックを使用します。通常アプリで使う場合はGit対象外の`data/generations/`、テスト・専用デモではOS一時フォルダ内です。既存企画・既存ドラフトは生成によって上書きしません。

確認画面の署名付きトークンは15分有効です。同じ実行IDの二重送信は既存結果を返し、Providerを再度呼びません。再起動時には確認画面を開き直してください。実行履歴は生成前確認から開けます。

形式・必須項目・創作禁止ルールの検証に失敗した結果は、ドラフトにも原文保管にも採用しません。正常な応答で下書き保存だけに失敗した場合、実行記録に検証済み原文を残し、「保存だけ再試行」で再検証・保存できます。生成は再実行せず、既に同じ実行から保存済みならそのドラフトを再利用します。

台帳破損、初期化後の台帳消失、残存ロック、アプリ中断による結果不明は自動リセットしません。実運用の記録を削除せず確認してください。記録全体のバックアップと復旧は人間による作業が必要です。同じ保存先を複数アプリで運用することは想定していません。

`lib/fact-policy.js`で手動生成・改善・直接生成の創作禁止方針を共有します。検査は限定した明確な断定（本人の収益・経歴・受賞など）や未確認のURL・数値の一部を検出するもので、事実確認ではありません。すべて未確認で保存し、公開前には人間の確認が必要です。

## 10. Phase 4・ステップ1：案件データ層

`schemas/offer.schema.json`、`lib/offers/validation.js`、`lib/offers/store.js`に案件の形式・検証・保存を追加しました。管理画面、企画への選択、AI生成との接続、実案件の登録はまだありません。このデータ層はネットワーク通信を行わず、既存企画・下書きの形式やファイルも変更しません。

- `createOfferStore(dataDirectory)`の`create(input)`で登録、`update(id, expectedRevision, input)`で全項目を置換更新します。`input`はスキーマの業務項目すべてを含め、`id / schemaVersion / revision / createdAt / updatedAt`はストアが付与します。移入用に`create(input, { id })`も使用できますが、既存IDは拒否します。
- `get(id)`は最新版、`list()`は案件一覧、`history(id)`は古い順の全revisionを返します。状態は`draft / active / paused / ended`。停止も更新で記録し、過去版は保持します。
- `<dataDirectory>/offers/<UUID>.json`に全revisionをまとめ、一時ファイルからのrenameで保存します。古いrevisionの更新を拒否し、ロックで別ストアとの同時書き込みも防止します。破損履歴や残存ロックは自動修復・削除しません。中断後は書き込み処理がないことを確認し、バックアップと照合して復旧してください。通常利用では`data/`全体をバックアップします。
- 出典・statement・成果地点のIDは、それぞれの種類内で案件全体に一意です。`source_checked`には存在する出典と確認日時が必要です。これは資料との照合済みを示し、広告効果の客観的な証明を意味しません。日時はタイムゾーン付きISO形式（秒必須、小数秒は3桁まで）です。
- 空の条件配列は未確認として保存します。有効な成果地点には確認済みの対象条件・成果条件・否認条件と公開可能なCTA、URLが必要です。案件の有効化には有効な成果地点と確認済みの禁止表現が必要です。「条件なし」は、資料に明記されている場合だけ出典付きstatementで登録してください。
- `getUsableStatements(offer, conversionId, now)`は有効期間内のactive案件・成果地点から、確認済みの`publishable`と`constraint_only`を分けて返すデータ層の関数です。`unverified`、`internal_only`、別成果地点の情報は返しません。期限・再確認期限の到達時も空になります。AI生成への接続はしていません。
- 未知の項目、認証情報入りURL、既知のAPIキー形式やCookie・パスワード等の記述を拒否します。入力値をエラーへ転載しません。ただし、名前や形式の分からない秘密文字列を完全に識別することはできません。認証情報や管理画面の全文は入力せず、必要な案件条件だけを登録してください。

追加テストは`test/phase4-offers.test.js`です。`npm test`で既存テストと一緒に実行し、架空データとOS一時フォルダのみを使用します。外向き通信は既存のnetwork guardで遮断します。

### Step 3：企画への案件・成果地点の紐付け

企画作成画面、または企画詳細の「企画を編集」から、案件名と成果地点名を選択し、任意の選択理由（1,000文字以内）を記録できます。案件は任意です。新規選択候補は`active`案件のみで、成果地点は自動選択しません。選択肢の切り替えにはJavaScriptが必要です。

- 同じ案件・成果地点で保存すると、名称とoffer revisionは固定されたままです。理由や通常の企画項目だけの変更でも維持します。選択を変えてから元に戻して保存した場合も同様です。
- 別案件・別成果地点へ変更した場合だけ、その案件の最新revisionで紐付けます。画面を開いた後に案件が更新された場合は409で拒否し、再選択を求めます。同じ組み合わせを最新revisionへ更新する専用操作はありません。

### Step 4：固定した案件情報をOpenAI直接生成へ接続

企画詳細の「AIで下書きを生成」から、既存の生成前確認画面を開きます。案件付きOpenAI生成では、固定した案件名・成果地点名・offer revision、現在のstatus／revision、選択理由、送信する案件情報の全項目を確認できます。確認ボタンを押したPOSTだけが生成を実行します。案件の自動選択、最新revisionへの自動追従は行いません。

`lib/ai/affiliate-context.js`が、serverで検証した案件履歴から`offerBinding.offerId / offerRevision / conversionId`に一致する版と成果地点を読みます。現在の案件は生成可否の確認に使用し、本文を固定版へ混ぜません。

| 情報 | 抽出方針 |
| --- | --- |
| 案件名・成果地点名 | 固定版から取得。企画側の表示snapshotを送信根拠にしない |
| facts・targetAudience・sellingPoints | `source_checked`かつ`publishable`で、出典付きのadvertiser／asp由来の本文だけ |
| 選択成果地点のeligibility・approvalConditions・rejectionConditions | 同じ公開基準で抽出。他成果地点の情報は抽出しない |
| prohibitedExpressions | 確認済みの`publishable`／`constraint_only`を生成上の禁止事項として使用。公開事実に昇格させない |
| CTA | 確認済み・公開可能なラベルだけ。URLは含めない |
| disclosure | schema上必須の広告明示本文・掲載位置だけ |
| 報酬・reward category・internal_only・unverified・editor由来 | 除外。editor由来は確認状態にかかわらず保守的に除外 |
| ASP管理情報・出典情報・URL・認証情報 | オブジェクトとして渡さない。URLを含むstatementも除外し、秘密情報は既存の検査で拒否 |
| 選択理由・各ID・revision・hash | 人間の確認とローカル根拠保存に使用。案件の送信snapshotには含めない |

`constraint_only`の成果条件は公開根拠として送信しません。空の条件配列は「条件なし」ではなく「公開可能な根拠が抽出されていない」ことを表します。必要なCTA／禁止表現を安全に抽出できない場合は生成を停止します。名前や広告明示にURLが含まれる場合も送信せず確認を求めます。通常の企画のテーマ・メモ等はPhase 3と同じ送信対象なので、確認画面で引き続き内容を確認してください。

現在の案件statusが`paused / ended / draft`なら警告を表示し、確認tokenと生成フォームを提供しません。固定版の案件・成果地点がactiveでない場合、現在の成果地点が停止／削除されている場合、固定版または現在版が有効期間外／確認期限超過の場合も停止します。企画の紐付けや案件履歴は変更しません。

署名付き・15分期限のconfirmationは、従来の企画／設定hashに加え、紐付け・公開snapshotの安定したSHA-256 hash・現在status／revisionを検証します。案件が更新されると古い確認は拒否されますが、新しい確認でも送信本文は元の固定版です。状態変更後にactiveへ復帰しても再確認が必要です。POST時と予算予約後の送信直前に再検証します。送信開始後の状態変更は、既に送信した要求を取り消すものではありません。

案件付きpromptは`direct-affiliate-v1`です。既存7項目と共通検証を維持し、案件情報を区切った補助資料として追加します。未登録情報・条件・URLの創作、禁止表現の使用、成果地点とCTAの混同、広告明示の削除を禁止します。送信前の抽出・状態検証・確認tokenにより、プロンプトだけに依存しません。案件付き入力はUTF-8バイト長にリクエスト付帯情報の余裕1,024を加え、設定済み入力上限を超える場合は切り捨てず停止します。厳密なトークン計算ではないため保守的な制限です。

生成draftの`affiliateContext`には`schemaVersion: 1`、`offerId`、`offerRevision`、`conversionId`、`selectionReason`、生成時の`offerName / conversionName`、`contextHash`と実際に送信した公開snapshotを保存します。draft画面で根拠を閲覧できます。案件本体・報酬・内部情報は複製しません。保存待ち／保存失敗でも同じ根拠と生成結果を台帳に保持し、再起動後の「保存だけ再試行」では現在案件を読み直さず、元のsnapshotの形・hash・prompt整合性を確認して保存します。APIの再呼出しや二重draft作成は行いません。案件がその後停止しても、既に生成済みの結果を保存することは可能です。

案件なしのOpenAI生成、既存Fake生成、手動Codex依頼文、改善依頼文、公開処理は従来のままです。Fakeは案件を使用しない固定の架空文章です。改善による子draftへの`affiliateContext`継承や、生成結果の案件条件・広告明示・禁止表現の網羅検査、公開可否の強化は今回追加していません。元draftは保持され、手動改稿は親draft参照で追跡できます。

検証は`npm test`（既存154件＋Step 4の35件＝189件）と`node scripts/browser-phase4-step4.mjs`です。ブラウザ検証はChrome・専用一時データ・架空案件・通信しないOpenAI SDK mockを使い、確認画面→明示生成→根拠保存→案件改訂後の旧版生成→paused時の古い確認拒否と生成停止、および375/1280px表示を確認します。外向き通信は遮断し、実API・実ASP・実案件を使用しません。

### Phase 4 Step 5.6：固定案件を継承する改善フロー

案件付き下書きの改善依頼を再開しました。依頼文は改善作業専用で、公開許可ではありません。block・未確認・検査失敗のある親でも修正依頼を作成できます。アプリからAIへの送信は行わず、従来どおり依頼文をコピーし、回答JSONを手動で取り込みます。

親に保存済みの固定affiliateContextと依頼時の本文7項目を専用schemaで保存します。依頼の取得・取込ごとにschema、本文/contextのhash、親とのbinding、設定、再構築したpromptとの一致をサーバーで確認します。現在の企画・最新案件から根拠を置換せず、revision・成果地点も自動変更しません。回答待ちに親を編集しても依頼時snapshotを使います。安全に確認できない旧案件付き依頼は拒否し、新しい依頼を作成してください。

案件付きpromptは本文・固定安全snapshot・改善設定だけを資料として使います。企画の最新メモや選定理由は追加しません。追加指示のURLと既存検出処理で認識できる秘密値を拒否します。既存本文・取り込み回答の既知の秘密値も拒否しますが、未知の秘密情報の検出を保証するものではありません。

改稿は未確認の新しい子draftです。親の公開準備・人間確認・warning確認・current/finalチェック・検査結果は引き継がず、同一本文でも子として新規にvalidationします。公開用本文の取得には子自身の検査・人間確認・公開準備・現在案件チェック・final export gateが必要です。検査失敗は本文/contextを保持してfailedとして保存し、再検査できます。案件なし改善・分析モードも維持しています。
