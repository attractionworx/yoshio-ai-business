# Yoshio AI Business

コンテンツのテーマや読者を整理し、このMacに保存するローカルWebアプリです。
ブログ・アフィリエイト記事、note、SNS、YouTubeなどの制作準備に使えます。

Phase 2では、企画からCodexへの生成依頼文を作り、Codexの回答を取り込んで編集・確認できます。このアプリは外部APIへ接続せず、自動投稿もしません。アプリの利用にAPIキーは不要です。Codexの利用料金・上限は利用中の契約と認証方式に従います。

## 1. 起動方法

Node.js 22以上を使用します。今回の環境ではNode.js 24で確認しています。

Macの「ターミナル」を開いて、次のコマンドを1行ずつ実行してください。

```bash
cd /Users/yoshio/yoshio-ai-business
npm install --cache .npm-cache --ignore-scripts --no-audit --no-fund
npm start
```

`npm install`は初回に実行します。追加のnpmパッケージに依存せず、Node.jsの標準機能だけで動きます。2回目からはフォルダへ移動して`npm start`だけで起動できます。

起動メッセージが出たら、SafariやChromeのアドレス欄に以下を入力してください。

**http://127.0.0.1:3000**

起動中はターミナルを開いたままにします。

### 使い方

1. 「コンテンツのテーマ」を入力します（必須・200文字まで）。
2. ターゲット読者を入力します（任意・500文字まで）。
3. 媒体をブログ / note / X / Instagram / YouTubeから選択します。
4. 目的（1,000文字まで）とメモ（5,000文字まで）を必要に応じて入力します。
5. 「企画を作成」を押すと保存され、整理した内容が表示されます。
6. 「企画一覧・新規作成へ」から、保存した企画を開いたり、新しい企画を作成したりできます。

前後の空白は取り除いて保存します。未入力の任意項目は詳細画面で「未入力」と表示します。各企画は独立したファイルになり、同じテーマでも別の企画として保存されます。詳細画面を再読み込みしても追加保存されません。

### 起動できないとき

- `node`や`npm`が見つからない場合は、Node.jsが利用できるターミナルか確認してください。
- 「ポート3000が使用中」と表示された場合は、先に起動したアプリのターミナルで`Control + C`を押してから再実行してください。
- 保存や表示に失敗した場合は、ターミナルのエラーと`data/`フォルダを確認してください。データを手動編集してJSONの形式が壊れると、読み込めなくなる場合があります。削除せずバックアップを取ってから確認してください。

## 2. 終了方法

起動に使ったターミナルで **Control + C** を押します（Commandキーではありません）。
ブラウザを閉じるだけではアプリは終了しません。終了後も企画ファイルは残ります。再び`npm start`で起動すると、保存済みの企画を開けます。

### 秘密情報とローカル利用

- APIキーなどの秘密情報をコードへ直接書かないでください。将来APIを追加するときは、環境変数などからサーバー側で読み込みます。
- `.env`、`.env.*`（`.env.example`を除く）、`secrets/`、秘密鍵、企画データ、npmキャッシュは`.gitignore`で除外しています。`.env.example`を作る場合はダミー値だけにしてください。
- 現段階では`.env`の読み込み処理はありません。秘密情報の入力も不要です。
- `.gitignore`はコードなどへ直接書いた秘密情報や、すでにGitへ登録済みのファイルを保護するものではありません。公開前には変更内容を確認してください。
- アプリは`127.0.0.1`だけで待ち受けます。ログイン機能はなく、このMacでの個人利用を想定しています。保存ファイルは暗号化していません。

実際のブラウザでも確認するには、Google ChromeがインストールされたMacでアプリを起動し、別のターミナルから以下を実行します。


## 4. Phase 2：Codexで下書きを作る手順

### ① アプリで企画を保存する

`npm start`で起動し、http://127.0.0.1:3000 を開きます。テーマ・ターゲット読者・媒体・目的・メモを入力して「企画を作成」を押します。保存済みの企画を一覧から開いても使えます。

### ② 依頼文をコピーしてCodexへ渡す

企画詳細の「1. Codexへの依頼文」にある「依頼文をコピー」を押します。Codexで新しい会話を開き、貼り付けて送信します。企画IDや出力形式も含め、依頼文全体を渡してください。回答待ちの間、アプリは開いたままで構いません。

コピーが許可されない場合は依頼文が選択されるので、Macでは **Command+C** でコピーできます。JavaScriptを無効にしている場合も、依頼文欄をクリックしてCommand+A、Command+Cでコピーできます。

アプリ自体は外部AIと通信しません。ただしCodexに貼り付けた情報はCodexへ渡ります。APIキー・パスワード・公開できない個人情報は含めないでください。APIを使わない運用では、Codex側もAPIキー認証ではなく、利用中のChatGPT契約での利用を選んでください。利用枠を超える追加購入はこのアプリでは行いません。

### ③ Codexの回答を取り込む

Codexは、次の7項目を含むJSON（アプリが読める形式の文章）を返します。

1. 企画概要
2. タイトル候補5個
3. 想定読者の悩み・検索意図
4. 記事・コンテンツの構成
5. 本文の下書き
6. CTA案
7. SNS告知文

Codexの回答をコピーし、企画詳細の「2. 生成結果を取り込む」へ貼り付けて「新しい下書きとして取り込む」を押します。JSONを囲むコードブロックや前後の説明文も含められます。回答が複数含まれる場合は、どれを使うか推測せず拒否するため、1つの回答だけを貼り付けてください。

コピーした文章に画面の折り返しが混ざると、文の途中に実際の改行と字下げが入り、JSONとして読み取れなくなることがあります。この場合は、文字列内の実改行と直後の字下げだけを除いたプレビューを表示します。JSONの`\n`で指定されている段落は保持します。

プレビューの時点では保存されていません。単語の間の空白や段落が意図どおりか確認し、「内容を確認して新しい下書きとして取り込む」を押してください。取り込まずに企画へ戻ることもできます。取り込み後も「貼り付け時の回答全文を見る」から補正前の文章を確認できます。

引用符やカンマの欠落、不正なエスケープ、同じ項目名の重複などは推測で修正しません。補正後も構文や必須項目が不正なら保存せず、エラーを表示します。

手でJSONを書く必要はありません。読み取りエラーになった場合は、画面のエラー文とともにCodexへ「このエラーを直して、元の企画ID・プロンプトバージョンを保ったJSON全体を再出力してください」と依頼します。エラー時は貼り付けた内容を画面に保持します。別企画の結果、7項目の欠落、タイトルが5個でない回答は保存しません。

取り込み直後の状態は必ず「未確認」です。APIによる自動生成や自動投稿は実行されません。

### ④ 7項目を編集して保存する

下書き画面で各項目を直接編集できます。タイトル候補は1行に1個、合計5行で入力します。「編集内容を保存」を押すと「編集中」になります。保存前にページを閉じると未保存の編集は残りません。

「AIが生成した原文を見る」を開くと、取り込み時の原文を確認できます。編集しても原文は変わりません。生成時の依頼文も確認できます。

### ⑤ 内容を確認済みにする

編集内容を保存し、事実・数値・リンク・表現などを読み直してから「確認済みにする」を押します。「確認済み」は人間が内容の確認を終えた記録です。このアプリから投稿はされません。

確認済みの文章を再編集すると、画面に「編集中（未保存）」と表示されます。保存すると保存データも「編集中」に戻ります。変更後はまず保存し、その後もう一度「確認済みにする」を押してください。変更せず保存した場合は確認済みを維持します。

### ⑥ 再生成と過去の下書き

既存の記事を改善する場合は、以下の「Phase 2.1」の手順を使ってください。親ドラフト付きの新しい版として保存できます。

「企画・過去の下書きへ」から元の企画に戻り、依頼文をもう一度Codexに渡します。修正したい方向性は、元の依頼文に添えてCodexへ伝えてください。元の企画IDとプロンプトバージョンを保ったJSONで回答するよう指定します。

結果を取り込むたびに新しい下書きができます。以前の下書きや編集内容は上書きされません。「過去の下書き」からそれぞれの原文・最新の編集内容・状態を確認できます。同じ下書き内の保存操作ごとの全履歴を残す機能ではありません。

複数のタブで同じ下書きを開いていた場合、古い画面からの保存は拒否されます。入力した文章を手元にコピーしてから、最新の下書きを開き直して反映してください。

## 5. 保存される情報とバックアップ

各下書きには、企画ID、生成時の企画、生成原文、貼り付けた回答全体、編集後の7項目、状態、確認日時、生成日時、取り込み日時、最終保存日時、生成方法、プロンプトのバージョン、生成依頼文を保存します。

生成方法は`codex-manual`です。生成日時はCodexの回答に含まれる申告値で、アプリが独立に検証した時刻ではありません。Codexで日時を取得できなければ`null`を返すよう依頼し、画面では「不明」と表示します。取り込み日時はアプリが実際に保存した時刻です。

`data/`全体はGit対象外です。アプリを停止し、フォルダ全体をコピーしてバックアップしてください。GitHubへコードを送っても下書きはバックアップされません。

バックアップはリポジトリ外の保護された場所に保存し、ファイル一覧とSHA-256で完全性を確認してください。

復旧する場合はアプリを停止し、現在の`data/`も別途バックアップしてから、アーカイブを新しい空フォルダへ展開して内容を確認してください。稼働中のプロジェクトへ直接上書きしないでください。

### 取り込み不具合の再発防止テスト

架空の検証専用文章を`test/fixtures/codex-note-response.json`、コピー時の折り返しを再現した文章を`test/fixtures/codex-pasted-wrapped.txt`に収録しています。実際の記事本文や企画IDは使用しません。後者には文字列内の折り返しが102か所あり、その除去後に7項目すべてが元の回答と一致することを検証します。

以前のテストは`JSON.stringify`で作った正しいJSONが中心で、画面からコピーした際の折り返しを検証できていませんでした。現在は`npm test`と`node scripts/browser-phase2.mjs`で、長文、説明文・コードブロック、折り返しを再現した回答、補正確認前の未保存、不正入力の拒否を検証します。ブラウザ検証では専用のクリップボード内容を使用するため、実行前に残したいコピー内容は別途控えてください。


## 7. Phase 2.1：下書き改善とバージョン履歴

### 通常の使い方

1. 企画から下書きを開きます。本文を編集した場合は先に「編集内容を保存」を押します。
2. 「AIで下書きを改善」の「改善依頼文を作る」を押します。
3. 表示された依頼文を「Codex用依頼文をコピー」でコピーし、Codexへ渡します。現在の企画と保存済みの人間編集版7項目を使用します。
4. この改善依頼画面を開いたままにし、Codexが返したJSONを貼り付けて「改稿を取り込む」を押します。画面のURLを保存しておけばアプリ再起動後も再開できます。
5. 改稿は必ず別ID・新しい版番号の「未確認」ドラフトになります。確認済みの親ドラフトや以前の版は変更されません。
6. 「バージョン履歴」からv1・v2・v3などを開き、状態・取り込み日時・改善方針・最新表示を確認します。元の下書きは「親ドラフトを開く」からも開けます。

通常は「読みやすくする」「初心者向けにする」「具体例を増やす」がONで、「完成稿を作る」を使います。「詳細設定」を開くと、「短くする」「SEOを意識する」「CTAを改善する」、自由入力の「その他の改善指示」（5,000文字以内）を指定できます。

実体験・収益・経歴・成功実績など、元データにない事実の創作禁止ルールはサーバー側で常に依頼文へ追加し、解除する設定はありません。具体例は仮の例と明示させます。既存ファイルを変更せず、まず回答として返す指示も含めます。AIの回答の事実性は人間が確認してください。

### 分析してから仕上げる

詳細設定の「まず分析だけする」を選ぶと、問題点・改善案・確認事項を返す依頼になります。分析結果の取り込みフォームは表示せず、サーバー側でも取り込みを拒否します。検討後、元の下書きで「完成稿を作る」を選び直し、必要な分析結果を「その他の改善指示」に反映して新しい依頼を作ります。

### 保存形式と互換性

- 新しいドラフトは`schemaVersion: 2`で、`versionNumber`（企画内の通し番号）、`parentDraftId`（改善元。初回・通常再生成はnull）、`improvement`（改善依頼のスナップショット）を追加します。編集保存回数の`revision`とは別です。
- `improvement`には設定、親の保存リビジョン、元本文、企画、依頼文、作成日時、依頼IDを保存します。回答待ちに親が編集されても、依頼作成時の内容を追跡できます。
- 改善依頼は`data/improvements/<依頼ID>.json`にも保存します。下書きと同様にGit対象外で、`data/`全体のバックアップに含めてください。
- 古いPhase 2ドラフトは移行・書き換えを行いません。版番号がないデータは取り込み日時順（同時刻ならID順）に表示用の番号を割り当て、新規ドラフトはその後に採番します。同じ企画の同時取り込みは1つのアプリ内で直列化します。同じデータフォルダへ複数のアプリを同時起動する運用は想定していません。
- 過去版から改稿すれば、その版を親とする分岐になります。版番号は枝ごとではなく企画全体の通し番号です。ツリー表示はありません。
- 改稿回答は企画ID・改善用プロンプトバージョン・依頼ID・親ドラフトIDがすべて一致する必要があります。通常の生成回答は従来の取り込み欄、改稿回答は対応する改善依頼画面に貼り付けます。
- コードブロック・周囲の説明文・安全な折り返し補正は既存処理を共有します。補正時はプレビュー確認後だけ保存し、貼り付け原文を保持します。曖昧な回答や壊れた入力を推測で補完しません。
- 同じ回答を再度取り込むと別の新規版になります。各版の「編集内容を保存」は従来どおりその版の人間編集欄を更新します。編集保存ごとの履歴は作りません。

状態は「未確認・編集中・確認済み」のままです。Phase 2.1では外部API連携、自動投稿、公開状態の管理は追加していません。

### 検証と実装前のバックアップ

```bash
npm test
node scripts/browser-phase2.mjs
node scripts/browser-phase2-1.mjs
```

Phase 2.1の自動テストはOSの一時ディレクトリを使い、ブラウザ検証もOSの一時フォルダに専用データ・Chromeプロフィールを作ります。通常の企画・ドラフトは使いません。ブラウザ検証はクリップボードを使用します。新しい検証では通常設定、コピー、新規改稿、親の確認済み保持、過去版、分析モード、未保存編集の誘導、320px・375px幅の表示を確認し、`result.json`と`mobile.png`を保存します。

Phase 2完成版は`phase2/codex-drafts`で保持します。バックアップはリポジトリ外の保護された場所に保存してください。復旧時はアプリを停止し、現在のデータを別途退避してから、空フォルダへ展開して確認してください。実際の記事・企画IDをテスト用ファイルへコピーせず、架空fixtureのみをGit管理します。


## 8. Phase 2.2：公開準備

1. 下書きを保存し、内容を確認して「確認済みにする」を押します。
2. 「公開準備・プレビューへ」を開き、5候補から公開するタイトルを明示的に選びます。
3. 「タイトル・確認項目を保存して公開前チェック」で選択を保存し、選択タイトル・本文・CTA・SNS告知文を検査します。
4. 要確認の箇所があれば下書きへ戻って修正・保存し、再度確認済みにします。
5. 実体験・経歴・実績、数値・収益・金額、外部リンクを人間が確認し、3項目すべてにチェックします。外部リンクがなければ「ないこと」を確認します。
6. 「公開準備OKにする」を押します。サーバーが毎回検査を行い、タイトル選択・検出事項なし・人間確認3項目が揃った場合だけ承認します。
7. 保存済みプレビューを確認し、タイトル・note本文・CTA込み本文・SNS告知文をそれぞれコピーします。note本文にはCTAを付けず、CTA込み本文は本文とCTAを空行で区切ります。タイトルは別にコピーしてください。

コピー結果は各ボタンの下へ表示します。失敗時は文章を選択するのでCommand+Cでコピーできます。コピーは公開準備OKのときに利用できます。画面内でタイトルや確認項目を変更すると、再保存までコピーを停止します。別タブで変更した場合は画面を再読み込みしてからコピーしてください。

下書きの「未確認・編集中・確認済み」とは独立して、公開準備を「未チェック・要修正・最終承認待ち・公開準備OK」で記録します。「最終承認待ち」は全条件を満たして公開前チェックを保存した後、明示的なOK操作を待っている状態です。「要修正」は仮記述の修正だけでなく、タイトル未選択・人間確認不足も含み、画面に理由を表示します。「公開済み」は追加していません。

機械検査は「要確認」、example.com/org/net、localhost、.test/.invalid等の明らかな仮URL、TODO/FIXME/TBD、【編集メモ】、{{差し込み項目}}、[URL]、URLや案内先の未定・後日差し替えなど、限定した記述を対象にします。公開対象でない概要・構成・未選択タイトルは検査しません。検出ゼロは事実性・リンクの有効性・公開の安全性の保証ではありません。外部サイトの取得、AIによる事実判定、API呼び出し、自動投稿は行いません。

本文など7項目の編集保存で内容が変わると、タイトル選択・機械検査・人間確認・公開準備OKを解除します。同じ内容の保存では維持します。AI改善で作る新しい版には承認を引き継ぎません。過去版はその版の保存済み内容を対象に準備できます。古い下書きは書き換えず未チェックとして開き、公開準備を保存したときにだけ`publication`を追加します。

実装は`lib/publish.js`（公開用データ生成・検査・条件判定）と`lib/publish-page.js`（画面）を分離しています。準備データは下書きの`publication`へ保存し、既存のリビジョン競合チェック・直列化・原子的ファイル保存を共有します。将来の接続処理で公開用データ生成を再利用できますが、今回外部投稿用APIはありません。

### 実機での手動確認（実データを使わない）

先に`node scripts/browser-phase2-2.mjs`を実行し、最後に表示された`dataDirectory`を以下の最後の引数へ貼り付けます。ブラウザ検証が作った架空企画・下書きをそのまま使えます。

```bash
node --input-type=module -e 'import { createApp } from "./server.js"; createApp({ dataDirectory: process.argv[1] }).listen(3001, "127.0.0.1", () => console.log("http://127.0.0.1:3001"));' "ここを表示されたdataDirectoryに置き換える"
```

Chromeで http://127.0.0.1:3001 を開き、架空企画→下書き→公開準備へ進みます。タイトルの変更・保存、確認項目を外した場合の承認拒否、全項目確認後の承認、4種類のコピーを試してください。下書きの本文に「要確認」を追加して保存すると、編集中になり公開準備への案内が変わります。再度確認済みにして公開前チェックを実行すると検出されます。修正・保存・再確認後に承認できることも確認してください。終了はControl+Cです。
