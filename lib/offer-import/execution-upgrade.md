# Configuration upgrade re-extraction: execution v3

This is a separate explicit operation, `configuration_upgrade_reextraction`, not a retry or a change to intentional reanalysis v2. Ordinary prepare continues rejecting duplicate material fingerprints and request hashes. v2 continues requiring identical configuration, estimate and request hash.

The source is a terminal lineage leaf with `failed_after_request`, validation-phase failure, known settled usage, zero reservation, no unknown/recovery flags, no validated artifact or planned/saved import, intact input and offer revision. Other unresolved work, uncertain persistence, corrupt/unknown profiles, locks and maintenance issues stop both preparation and sending. Provider must remain the same; destination is the current registered configuration and must differ. Returning to any configuration already used by an ancestor is forbidden. A source has at most one child across dedicated operations; source/destination configuration pairs and operation IDs are unique.

Only the source detail page offers `/offer-extractions/:sourceId/configuration-upgrade`. Read-only historical display uses the recorded profile; displaying history does not authorize a connection. Unchecked preparation approval binds operation kind, source ID/revision/record hash, old configuration/request hashes, input hash, destination configuration/request hashes, full destination payload/profile/estimate binding, operation ID and child ID. Tokens expire after 15 minutes and on restart. Preparation creates a distinct v1 input artifact with exactly the source content and a new v3 prepared record, without reservation or provider call. Repeating that same operation can return only its durably saved prepared child. A different operation cannot create a second child.

The v3 record has immutable `upgrade` lineage and `profileSnapshot` (snapshot contract v1). It does not copy the parent's configuration, usage, costs, errors or approval. Current model, configuration, instructions, request hash and estimate are generated afresh. Source revisions are never written. Sending approval separately binds child/prepared revision, exact payload, configuration, profile snapshot, input artifact, estimate and lineage; reserve current maximum cost under the shared lock. Only a durable `sending` transition owner invokes the provider. Existing state transitions, unknown reservation retention and explicit local save-only recovery are reused. Configuration or target changes after preparation stop sending rather than updating the child.

Ledger envelope v3 mixes unchanged v1/v2 revisions and new v3 histories. The v3 dispatcher reuses strict v1 state/history checks and exact v2 same-configuration graph conditions. Source references must point backwards to terminal latest records; cycles, branches, duplicate operations/pairs, altered materials and invalid bindings fail. New normal records remain v1. Startup/read never migrates, resumes, repairs, resends or switches data directories.

## Historical profile audit and current sending permission

Historical configuration hash self-consistency, original request hash, material fingerprint, input bytes, usage charges and reservations are checked using each record's own settings. OpenAI historical requests and input estimates are reconstructed only through a known pure builder, never code from a snapshot. The registry pins exact canonical profile digests for three exact releases: original instructions, strengthened candidate-combination instructions, and the quote-contract instructions with wire descriptions. The two prior snapshots remain unchanged. The new release is registered from the current implementation, without rewriting any execution. The original release configuration hash was verified as `1e7dfc3566e9e310e296aa6187159629ce31467a69f5b021c349a608dc953d1e`, matching both existing records without any ledger update. The strengthened release hash is `4acd6caa8e45b618df0f059f27a0e2adc9137e02e835c2d3800818dac6c33f71`.

v3 snapshots store the complete public registered profile (instructions, wire schema, pricing/limits, model, estimator and implementation identities), or a strictly simulation-only fake profile. Snapshots are data only; credentials, response fragments and source bodies are not added. Real snapshots must match a known pinned release/current profile. Unknown profiles/builders, missing snapshots, corruption and invalid lineage remain errors; a difference from the current sending profile alone is not an error. Hashes detect inconsistent changes, not coordinated forgery of an entire unsigned audit history. Before future profile/builder changes, archive the exact prior release and preserve a trusted implementation for its audit. Never infer a profile from record hashes or waive unknown-profile errors.

Current provider/model/configuration checks remain mandatory for sending. Historical validation does not register a provider, authorize an old configuration, or permit automatic resend. v3's snapshot is mandatory and immutable in every revision.

## Budget, backup and other boundaries

The shared coordinator aggregates all versions using their own recorded usage/prices. Preparation books/reserves nothing; sending approval adds the new child's current maximum reservation. Past charges, activation, real approval, stop amounts and unknown reservations are unchanged.

Maintenance inspects the same seven stores with version-aware ledger validation and historical profile audit. v3 backups use manifest v3 and `contracts.extractionExecution=3` and `contracts.extractionProfileSnapshot=1`, keeping the existing allowlisted files/directories. Snapshot lives in the ledger, not a new store. Manifest/ledger versions must agree. New readers accept old manifest v1/v2 and old ledger v1/v2, explicitly reporting absent upgrade coverage; v1 excludes AI coverage. Dry-run uses backed-up immutable settings and never restores or modifies data. Readers predating v3 cannot read v3 histories; downgrading is not supported after explicit v3 preparation.

Offer/import/artifact/candidate schemas, candidate acceptance conditions, review, reflection, publication and active boundaries are unchanged. Only succeeded extraction connects to pending/unverified review. Diagnostics use fixed safe vocabulary; raw responses/exceptions are not persisted or displayed. Fixture tests use OS temporary directories and fake providers, with an external-network guard; they do not exercise live activation, real API calls or DMM data.


Quote mismatch diagnostics retain the reference → range → exact equality → duplicate validation order. The equality guard remains `doc.text.slice(start,end) === quote`. Only after a mismatch, classification checks: (1) an exact quote occurrence at a different start within the same block, (2) different UTF-16 lengths, (3) same-length content mismatch. A match at the supplied start with a wrong end alone is a length mismatch, not “elsewhere”. Repeated text can satisfy the first observation even if the supplied start also matches a prefix. These codes report observations, not causes; no repair, normalization, quote/body/response fragments, diagnostic hashes or candidate/evidence indices are persisted. Legacy `validation_quote` remains readable. Existing audit response hashes remain unchanged.

Wire descriptions annotate evidence fields only. Removing descriptions yields exactly the previous wire schema; extraction/import/artifact acceptance schemas and execution/snapshot version numbers are unchanged. The prompt identifies decoded JSON text, document-origin zero-based UTF-16 units and end-exclusive offsets, with surrogate-pair and CRLF examples. Strict-output wire descriptions are supported in OpenAI's Structured Outputs documentation; no real provider call is used for verification.


The separate [execution v4 contract](execution-v4.md) introduces positionless wire v2 with exact local quote resolution. v1/v2/v3 records and their audit meanings remain unchanged. Current-profile upgrades using this processing create v4 children; legacy v3 upgrades remain on their own validation path.
