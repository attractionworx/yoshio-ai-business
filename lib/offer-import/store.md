# 取り込み保存層 — Step 2

Step 1の `contract.md` と2つのJSON Schemaは変更しない。
この保存層はHTTP/UI、AI Provider、正式offerへの反映、公開許可には接続しない。

## API

`createOfferImportStore(dataDirectory, { now })` を使用する。nowはテスト用に差し替え可能。
本番の保存先は呼出側が指定する。このStepのテストはOS一時フォルダだけを使用する。

- `create({ targetOffer, documents, extraction }, { id } = {})`：Step 1の純粋関数で初期候補を作成・保存。
  管理項目やレビュー済みdraftは受け取らない。ID指定を省略するとUUIDを生成する。
- `review(id, candidateId, expectedRevision, { decision, edited, sourceChecked, reason })`：
  Step 1のreviewCandidateを通し、新しいrevisionを保存。日時はstoreが付与し、入力atは拒否する。
- `get(id)`：最新版。`history(id)`：古い順の全版。`list()`：各記録の最新版。
  読取操作はファイル／ディレクトリを作成・修正しない。

任意のdraft置換、資料・AI原文・対象案件の変更、削除、offer入力生成、正式保存のAPIは提供しない。
sourceCheckedは、後続のUIで人間が個別照合した操作を渡すための入力。
store自身は人間の本人性を認証しない。後続HTTPはOrigin・操作の認可等を実装する必要がある。

## 保存と履歴

`<dataDirectory>/offer-imports/<UUID>.json` に
`{ schemaVersion: 1, revisions: [Step 1形式のdraft, ...] }` を保存する。
各reviewで履歴を追加し、同じ内容の明示操作もrevisionを増やす。
各版の全資料と候補を保持するため、資料量・レビュー回数に応じてファイル容量と読取コストが増える。
Step 3前に想定資料量で実用性を確認する。無断の履歴圧縮・削除・形式変更は行わない。

読取時は全版をStep 1 validatorで再検証し、初版がすべて未確認・保留であることを確認する。
後続版ではID・資料・AI原文・対象案件・作成日時が不変で、1候補のレビュー操作を再実行して
同一版を再現できることを確認する。複数候補を同時に変更した不正履歴も拒否する。
hashやこの履歴検証は電子署名ではない。整合する履歴全体の書換え／切詰めの真正性は保証しない。

一時ファイルをwx・0600で書き、renameで履歴ファイル全体を原子的に置換する。
ディレクトリは0700。同一store内の書込みを順序化し、専用.lockディレクトリで
別store／別プロセスの同時書込みを拒否する。expectedRevisionもロック内で照合する。
rename前の失敗では旧ファイルを維持する。異常終了の.tmpは読取時に無視し、自動昇格／削除しない。
ファイル／専用ディレクトリのシンボリックリンクは拒否する。
fsyncによる電源断時の永続性や、外部プロセスによる悪意あるファイル差替えを保証するものではない。

## 失敗と復旧

- 400：入力不正。既知の秘密情報等はStep 1の検証で拒否し、内容を保存しない。
- 404：指定記録なし。
- 409：重複ID、古いrevision、書込み中／残存ロック。
- 503：破損履歴、不正な状態遷移、入出力失敗等。入力・例外・パスをエラーへ転載しない。

破損記録や残存ロックを自動修復・削除しない。履歴全体をバックアップし、処理が動いていないことを
確認して人間が復旧する。ロック解除や一時ファイル除去に失敗した場合も成功と断定せず停止する。
rename後に応答／ロック解除が失敗した場合は最新版を読み直す。旧revisionでの再送は409となる。
保存先ファイル自体が消失した場合、その存在を別台帳で証明する仕組みはまだない。

テストではfileSystemオプションに標準fs互換fakeを注入し、書込み／rename失敗を検証する。
これはProviderや外部APIの接続口ではない。実API・.env・実案件データは使用しない。

## Step 3前の確認

人間レビューUIで、採用・修正・却下と個別照合をどう提示するか確認する。
保存失敗／409後の再読込と入力の扱い、既存記録へのアクセス制御、バックアップ・容量運用を確認する。
正式offerへの差分生成・反映はStep 4の範囲。Step 3でも候補を公開根拠に利用しない。
