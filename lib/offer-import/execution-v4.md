# Exact quote resolution: execution v4

Wire v2 returns the same candidate fields and evidence consisting only of documentId, blockId and quote. start/end and all other evidence fields are rejected. The source block's decoded text is searched without trimming, Unicode/line-ending normalization, fuzzy matching or cross-block fallback. An overlapping second occurrence is ambiguity. Only a unique occurrence produces document-origin zero-based UTF-16 start and end-exclusive end. The result uses the unchanged internal extraction schema v1 and existing candidate/evidence validator. Empty/nonunique matches stop the entire extraction; no partial artifact/import is saved.

`processingContract` is immutable from prepared and includes exact wire/internal schema hashes, resolver/inverse versions and pinned implementation/validator hashes. Profile snapshot v2 includes that same contract. The registered resolver is code owned by the application, never executed from snapshot data. Keep the v1 algorithm/validator implementation intact when introducing a future resolver version; unknown versions or hashes stop rather than guessing.

The responseHash continues identifying the canonical JSON-parsed provider envelope {extraction,usage}, now containing wire v2. It is not a hash of HTTP bytes or a provider signature. After successful resolution, the existing immutable validated_extraction artifact holds only {inputHash,extraction}, using internal schema v1. No wire/raw-response artifact is added. At the validated transition, `resultBinding` binds input hash, response hash, validated artifact hash and processing contract hash, and cannot change afterwards. The inverse strips only generated start/end, restores schemaVersion 2, and preserves candidate/evidence order and all other values. Runtime compares the inverse with the original wire before persistence. Audit reconstructs wire from the artifact, verifies responseHash with recorded usage, replays exact resolution against the immutable input, and compares the entire internal result. This detects inconsistent tampering; it does not prove AI provenance or defend against coordinated rewriting of every unsigned record.

Known usage is settled and reservations released before resolution. Resolution failures use fixed validation_wire_schema, validation_quote_not_found or validation_quote_ambiguous codes; overlapping matches are included in ambiguous. Existing candidate/evidence diagnostics remain unchanged after conversion. No failed response body, quote, candidate/evidence index or diagnostic-specific hash is saved. A failed record retains the existing responseHash and usage but cannot prove the unavailable failed quote retrospectively. resultBinding remains null until validated.

v4 supports ordinary new extraction and explicit configuration_upgrade_reextraction. Dedicated upgrades retain terminal eligible failed_after_request leaf restrictions, identical input/metadata/offer revision, different destination configuration, no ancestor configuration reuse, one child per source, unique operation and two human approvals. Destination profile and processing identity are bound before creation and again before reservation/sending. Old same-configuration v2 remains unchanged for its legacy processing; v2 records do not represent a v4 resolver, and no new same-configuration v4 operation is added.

Sending/unknown/recovery and budget semantics are unchanged. Only a durable sending owner calls the provider. Missing/unknown usage holds the reservation. Response/validated artifact/import persistence uncertainty stops; no automatic repair, replay or resend is added. Audited existing artifacts may be used only by the existing explicit local save/finalize recovery. Orphans remain human-review issues. A restart invalidates preparation/send tokens; durable prepared children are not automatically resumed.

The ledger v4 reader preserves v1/v2/v3 rows verbatim and validates their old record/state/profile semantics. Mixed histories validate lineage against original rows, not rewritten projections. Old wire v1 profiles remain exact registered snapshots. The historical pure request builder stays byte-for-byte intact. Current profile mismatch is a send restriction, not a historical integrity error. Internal offer/import/artifact schemas, review/reflection/publication/active boundaries and candidate acceptance conditions remain unchanged.

Maintenance replays v4 audit with the recorded trusted processing/profile, and validates source graph and downstream imports. Backup manifest v4 declares execution 4, profile snapshot 2, wire 2 and evidence resolution 1 with the same store/file allowlists. Manifest versions 1-3 remain readable; older backups can warn about replacement of current data while their own integrity remains valid. Restore dry-run never restores or mutates stores. There is no startup migration, real restore, automatic activation or automatic resend. Readers predating v4 cannot read a ledger after explicit v4 creation; downgrade is unsupported.

Tests use fictional OS-temp fixtures, fake providers and existing isolated SDK stubs only. A network guard rejects external Node connections. Chrome display verification uses a separate temp profile and localhost fixture with outbound DNS/proxy restrictions; no operational server is used. Operational files must retain their hashes and file list throughout implementation/verification.
